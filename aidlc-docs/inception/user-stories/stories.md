# ユーザーストーリー: 夫婦間API Gateway

## 1. ストーリー生成方針

User Stories Planning の回答に基づき、ストーリーは **ハイブリッド方式** で整理する。

- 主要ストーリーはユーザージャーニーベース
- 補助ストーリーは機能ベース
- 受け入れ基準は箇条書きと Given / When / Then を併用
- 主役は「不満を入力する配偶者」
- AI同士の家族会議はMVPの中心体験
- StandardをMVPの基本体験とし、Proは将来拡張に限定
- 安全制御はUser Storiesでは標準粒度で扱い、詳細は後続設計へ送る

## 2. エピック一覧

| Epic | 名称 | 目的 |
|---|---|---|
| E-01 | 夫婦間あるある導入 | 家庭内の言いにくさを短時間で伝える |
| E-02 | Standard中心の言い換え体験 | 不満入力、地雷ワード検出、言い換えを成立させる |
| E-03 | プラン差分と事業性 | FreeとStandardの差を見せ、Proを将来拡張として説明する |
| E-04 | AI同士の家族会議 | 「人をダメにする」テーマを体験として表現する |
| E-05 | 安全性と審査員向け説明 | ブラックユーモアへの懸念をケアする |

## 3. MVPユーザーストーリー

### US-01: デモ家庭としてログインする

**As a** 不満を入力する配偶者  
**I want** デモ用の家庭アカウントで簡単にアプリを開始したい  
**So that** すぐに家庭内の言いにくいことを入力できる

#### 関連ペルソナ

- P-01: 不満を入力する配偶者
- P-03: 共働き家庭

#### 受け入れ基準

- デモ用ログインで1家庭のデータにアクセスできる
- ログイン後に家庭内タスクや相手プロフィールの初期状態が表示される
- 本番品質の同意管理や詳細な権限管理はMVP範囲外であることが分かる

#### Given / When / Then

- Given デモ利用者がアプリを開いている
- When デモアカウントでログインする
- Then 佐藤家のデモ環境が表示される

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | 他ストーリーの前提だが、ログイン体験として独立して確認可能 |
| Negotiable | 認証方式は後続設計で調整可能 |
| Valuable | デモ開始を短くし、審査員に体験を見せやすくする |
| Estimable | 簡易ログインとして見積もり可能 |
| Small | 1画面相当の小さなストーリー |
| Testable | デモ家庭が表示されることで確認可能 |

### US-02: 言いにくい不満をそのまま入力する

**As a** 不満を入力する配偶者  
**I want** 洗い物や家事分担への不満をそのまま入力したい  
**So that** 自分で綺麗な言い方を考えなくてもAIに変換してもらえる

#### 関連ペルソナ

- P-01: 不満を入力する配偶者

#### 受け入れ基準

- ユーザーは家庭内タスク、感情、相手への依頼を含む文章を入力できる
- 空入力は送信できない
- 入力例が家庭内あるあるとして伝わる
- モバイルファーストWebアプリとして片手でも入力しやすい構成にする

#### Given / When / Then

- Given 美咲が朝の洗い物に不満を持っている
- When 「昨日の洗い物が残っていてつらい。責めたいわけではないけど、今日中にやってほしい」と入力する
- Then システムは次のリスク判定へ進める

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | 入力体験として単独確認可能 |
| Negotiable | 入力項目や例文は調整可能 |
| Valuable | 主役ユーザーの最初の痛みを表現する |
| Estimable | UI入力フォームとして見積もり可能 |
| Small | 1機能に絞られている |
| Testable | 入力可否、空入力制御で確認可能 |

### US-03: 地雷ワードと家庭内炎上リスクを確認する

**As a** 不満を入力する配偶者  
**I want** 自分の入力に含まれる地雷ワードと炎上リスクを知りたい  
**So that** 送る前に、相手を逆撫でする可能性に気づける

#### 関連ペルソナ

- P-01: 不満を入力する配偶者
- P-02: メッセージを受け取る配偶者

#### 受け入れ基準

- 「いつも」「なんで」「普通は」「私ばっかり」「前も言ったよね」などを検出できる
- 家庭内炎上リスクを数値またはラベルで表示できる
- 表示はコメディとして伝わるが、危険な誘導にはならない
- 検出結果は後続の言い換え生成に使われる

#### Given / When / Then

- Given ユーザーが不満文を入力している
- When 入力に地雷ワードが含まれる
- Then システムは検出された地雷ワードと家庭内炎上リスクを表示する

#### PBT一部適用候補

- 地雷ワード検出は純粋関数としてPBT対象候補
- 炎上リスクスコア計算は範囲制約や分類不変条件のPBT対象候補

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | リスク判定機能として独立して確認可能 |
| Negotiable | スコア表現や地雷ワード一覧は調整可能 |
| Valuable | あるあるコメディと安全性の両方を支える |
| Estimable | ルールベース + AI補助として見積もり可能 |
| Small | 判定表示に絞られている |
| Testable | 入力に対する検出結果で確認可能 |

### US-04: StandardプランでAIに言い方をおまかせする

**As a** 不満を入力する配偶者  
**I want** 言いたいことだけ入力すれば、AIに言い方を自動調整してほしい  
**So that** 自分で細かいトーン指定を考えなくてよくなる

#### 関連ペルソナ

- P-01: 不満を入力する配偶者
- P-02: メッセージを受け取る配偶者

#### 受け入れ基準

- Standardプランでは、ユーザーが細かい指示をしなくても文面が生成される
- 生成文は元の意図を保ちつつ、責める表現を弱める
- 受け取り側が依頼として理解しやすい文面になる
- Freeプランとの差として、「手動指示が不要になる」ことが分かる

#### Given / When / Then

- Given ユーザーがStandardプランを選んでいる
- When 不満文を入力して生成を実行する
- Then AIは相手に伝わりやすい文面を自動生成する

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | 言い換え生成として独立確認可能 |
| Negotiable | トーンや文体は調整可能 |
| Valuable | MVPの中心価値である |
| Estimable | Bedrock生成 + ルール適用として見積もり可能 |
| Small | Standardの生成体験に絞られている |
| Testable | 生成結果の存在、禁止表現抑制、意図保持で確認可能 |

### US-05: FreeとStandardの差から事業性を見せる

**As a** ハッカソン審査員  
**I want** FreeとStandardの違いを短時間で理解したい  
**So that** このサービスが単なるネタではなく、マネタイズ可能なプロダクトに見える

#### 関連ペルソナ

- P-01: 不満を入力する配偶者
- P-04: ハッカソン審査員

#### 受け入れ基準

- Freeでは細かい指示が必要で、設定が静的なため外すと逆撫でする可能性がある
- Standardでは言いたいことだけ入力すればAIが基本自動調整する
- 価格が上がるほどユーザーが考えなくなる構造が見える
- 事業性がブラックユーモアと矛盾せずに説明される

#### Given / When / Then

- Given 審査員がプラン比較を見る
- When FreeとStandardの処理結果を比較する
- Then Standardの価値と課金理由を理解できる

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | プラン比較として独立確認可能 |
| Negotiable | 価格やプラン名は変更可能 |
| Valuable | 事業性を伝える |
| Estimable | デモ表現として見積もり可能 |
| Small | Free/Standard差分に限定 |
| Testable | 比較表示で確認可能 |

### US-06: Guardrailsとアプリルールで危険な文面を抑制する

**As a** 不満を入力する配偶者  
**I want** 攻撃的・強制的・操作的なメッセージを抑制してほしい  
**So that** ブラックユーモアのサービスでも、安全性への配慮を示せる

#### 関連ペルソナ

- P-01: 不満を入力する配偶者
- P-02: メッセージを受け取る配偶者
- P-04: ハッカソン審査員

#### 受け入れ基準

- Bedrock Guardrailsとアプリケーションルールを安全制御として説明できる
- 高リスクな文面は警告または再生成対象になる
- 「自動送信」はデモ演出として慎重に扱う
- 詳細な同意、監査ログ、手動承認は後続設計で扱うと明記される

#### Given / When / Then

- Given 入力または生成結果に攻撃的な表現が含まれている
- When 安全制御が実行される
- Then システムは警告、抑制、再生成のいずれかを行う

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | 安全制御ストーリーとして確認可能 |
| Negotiable | 制御粒度は後続設計で拡張可能 |
| Valuable | ブラックユーモアへの懸念をケアする |
| Estimable | Guardrails + ルールで見積もり可能 |
| Small | 標準粒度の安全制御に限定 |
| Testable | 高リスク入力に対する警告・抑制で確認可能 |

### US-07: AI同士の家族会議を見る

**As a** 不満を入力する配偶者  
**I want** 自分と相手のAIが家庭内議題を整理し、合意形成する様子を見たい  
**So that** 便利さと、人間が直接話さなくなる怖さの両方を体験できる

#### 関連ペルソナ

- P-01: 不満を入力する配偶者
- P-02: メッセージを受け取る配偶者
- P-03: 共働き家庭
- P-04: ハッカソン審査員

#### 受け入れ基準

- 妻AI、夫AI、調停AIのような役割が画面上で分かる
- 洗い物、保育園準備、買い出しなどの議題が整理される
- AI同士が合意案を作る流れが表示される
- MVPの中心体験として扱われる

#### Given / When / Then

- Given ユーザーが言い換え結果を確認している
- When AI同士の家族会議を開始する
- Then 各AIが議題を整理し、家庭内合意を生成する

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | 家族会議シミュレーションとして確認可能 |
| Negotiable | AI役割名や会話内容は調整可能 |
| Valuable | テーマ適合の中核 |
| Estimable | シミュレーション表示として見積もり可能 |
| Small | 合意形成デモに限定 |
| Testable | 議題、AI発話、合意結果の表示で確認可能 |

### US-08: ラスト画面でブラックユーモアを伝える

**As a** ハッカソン審査員  
**I want** 最後に「家庭内摩擦は下がったが、直接会話もなくなった」ことを見たい  
**So that** このサービスが単なる便利ツールではなく、AI依存社会への風刺だと理解できる

#### 関連ペルソナ

- P-03: 共働き家庭
- P-04: ハッカソン審査員

#### 受け入れ基準

- ラスト画面に「合意形成: 成功」「家庭内摩擦: 低下」「直接会話: 0件」「関係性の自律性: 低下」を表示する
- ブラックユーモアが強すぎて危険サービスに見えないよう、安全制御への配慮も補足する
- 「人をダメにする」テーマが明確に伝わる
- コメディからブラックユーモアへの流れが自然である

#### Given / When / Then

- Given AI同士の家族会議が完了している
- When ユーザーが結果画面を見る
- Then 家庭内摩擦低下と直接会話0件が同時に表示される

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | ラスト演出として独立確認可能 |
| Negotiable | 指標名や文言は調整可能 |
| Valuable | テーマ適合を強く伝える |
| Estimable | 結果表示画面として見積もり可能 |
| Small | ラスト画面に限定 |
| Testable | 指標表示と文言で確認可能 |

### US-09: AWS活用の説明材料を得る

**I want** どのAWSマネージドサービスを何に使うのか理解したい  
**So that** 企画がAWS Summitのハッカソンに適していると判断できる

#### 関連ペルソナ

- P-04: ハッカソン審査員

- Bedrockは言い換え生成に使う候補として説明される
- Bedrock Guardrailsは安全制御に使う候補として説明される
- DynamoDBは家庭設定や会話履歴保存に使う候補として説明される
- アーキテクチャ主案はWorkflow Planningで比較・決定すると明記される

#### Given / When / Then

- Given 審査員が企画資料を確認している
- When AWS構成説明を見る
- Then 各AWSサービスの役割を理解できる

#### INVEST確認

| 観点 | 評価 |
|---|---|
| Independent | ピッチ・設計説明として独立 |
| Negotiable | 採用サービスはWorkflow Planningで変更可能 |
| Valuable | AWS活用の説得力を高める |
| Estimable | 資料作成・設計整理として見積もり可能 |
| Small | サービス役割説明に限定 |
| Testable | 資料にサービスと用途が明記されていることで確認可能 |

## 4. 将来拡張ストーリー

### FS-01: Proプランでバイタル情報から送信タイミングを制御する

**As a** 不満を入力する配偶者  
**I want** 相手の状態に応じてAIが伝えるタイミングを選んでほしい  
**So that** 自分がタイミングを考えなくても、相手を逆撫でする可能性を下げられる

#### 位置付け

このストーリーはMVPではなく将来拡張である。  
MVPではStandardを基本体験とし、Proはピッチや将来構想として説明する。

#### 将来受け入れ基準

- 相手の明示的同意を前提に、スマートウォッチ等のバイタル情報を扱う
- 心拍、睡眠、活動量、ストレス傾向などから送信タイミングを推定する
- タイミング制御の判断理由を説明できる
- 詳細な同意管理、監査ログ、手動承認を後続設計で扱う

#### PBT一部適用候補

- 疑似バイタル情報の入力正規化
- バイタル情報JSONの保存・復元
- タイミング分類の範囲制約

## 6. PBT一部適用対象

Property-Based Testingは一部適用である。  
User Stories時点では、以下を後続の設計・実装でPBT候補として扱う。

| 対象 | 関連ストーリー | PBT観点 |
|---|---|---|
| 地雷ワード検出 | US-03 | 検出結果の不変条件、入力文字列の多様性 |
| 炎上リスクスコア計算 | US-03 | スコア範囲、分類境界、禁止値が出ないこと |
| プラン別制御ロジック | US-04, US-05 | Free / Standard の分岐が入力条件に対して一貫すること |
| 家庭設定JSON保存・復元 | US-01, US-07 | シリアライズ往復で値が壊れないこと |
| 疑似バイタル情報の正規化 | FS-01 | 範囲制約、欠損値処理、分類結果の安定性 |
