# 要件定義書: 夫婦間API Gateway

## 1. 要件分析サマリー

### 1.1 ユーザー要求

AWS Summit ハッカソン向けに、「人をダメにするサービス」というテーマで **夫婦間API Gateway** の企画を AI-DLC の Inception Phase に従って整理する。

サービスは、家庭内の言いにくいことをAIが角の立たない表現に変換し、必要に応じて相手への伝達やAI同士の家族会議まで代行する。  
風刺の中心は、AIが家庭内摩擦を減らすほど、人間が自分の言葉で向き合う力を失う点にある。

## 2. プロダクト概要

**夫婦間API Gateway** は、共働き家庭や同居生活で発生する「言いにくいこと」を、AIが相手に合わせて翻訳・調停する家庭内交渉サービスである。

ユーザーは、洗い物、ゴミ出し、育児、家計、義実家対応などの不満や依頼を入力する。  
システムは家庭内炎上リスク、地雷ワード、相手の傾向をもとに、角が立ちにくい表現へ変換する。

ハッカソン上の見せ方としては、以下を重視する。

- 入り口は家庭内あるあるのコメディとして理解しやすくする
- 出口は「直接会話: 0件」というブラックユーモアで落とす
- AWSマネージドサービスの利用理由を自然に説明できる構成にする
- Free / Standard / Pro の価格差が「人をダメにする」度合いに連動するように見せる

## 3. 対象ユーザー

### 3.1 主要ユーザー

- 共働き夫婦
- 子育て世帯
- 同居カップル
- ルームシェア世帯

### 3.2 拡張ユーザー

- 親や義実家との距離感に悩む家庭
- 家事分担や育児分担の会話で揉めやすい家庭
- 家庭内の会話を減らしたいが、家庭内摩擦も減らしたい人

## 4. 機能要件

### FR-001: 不満・依頼入力

ユーザーは、家庭内で言いにくい不満、依頼、謝罪、フォローアップ内容をテキストで入力できる。

受け入れ条件:

- 入力欄はモバイル画面で使いやすいこと
- 入力内容は家庭内タスク、感情、相手への依頼を含められること
- 空入力は送信できないこと

### FR-002: 家庭内炎上リスク判定

システムは入力文から、家庭内で揉める可能性のある表現を検出し、炎上リスクを表示する。

受け入れ条件:

- 「いつも」「なんで」「普通は」「私ばっかり」「前も言ったよね」などの地雷ワードを検出できること
- 検出結果をユーザーに分かりやすく表示すること
- リスク表示はコメディとして見せつつ、危険な誘導にならないこと

### FR-003: 言い換え生成

システムは入力文を、相手に伝わりやすく角が立ちにくい文面へ変換する。

受け入れ条件:

- 元の意図を失わずに、攻撃的・責める表現を弱めること
- Free / Standard / Pro のプラン差を反映できること
- 生成結果は送信前にユーザーが確認できること

### FR-004: プラン別挙動

価格が上がるほど、ユーザーが考えなくてもよい設計にする。

| プラン | 要件 |
|---|---|
| Free | ユーザーが細かく指示する必要がある。相手設定は静的で、外すと逆撫でする可能性がある |
| Standard | ユーザーは言いたいことだけ入力する。AIが履歴やNGワードをもとに基本自動調整する |
| Pro | 疑似バイタル情報を使い、文面だけでなく伝えるタイミングまでAIが制御する |

受け入れ条件:

- プラン差がデモ上で明確に分かること
- Proでは「人間が何も考えなくてよくなる」ことが明確に表現されること
- Proのバイタル連携はMVPでは疑似データ入力で表現すること

### FR-005: AI同士の家族会議シミュレーション

MVPでは、ユーザー本人同士ではなく、AI同士が家庭内合意を形成するシミュレーションを含める。

受け入れ条件:

- 妻AI、夫AI、調停AIのような役割を画面上で表現できること
- 合意形成の結果として、洗い物、保育園準備、買い出しなどの議題が整理されること
- ラスト画面で「直接会話: 0件」「家庭内摩擦: 低下」「関係性の自律性: 低下」を表示できること

### FR-006: 疑似バイタル情報入力

Proプランでは、相手の状態を表す疑似バイタル情報を入力または選択できる。

受け入れ条件:

- ストレスレベル、睡眠状態、心拍傾向、活動量などを疑似データとして扱えること
- AIは疑似バイタル情報をもとに、伝えるタイミングの推奨を返すこと
- 実際のスマートウォッチ連携はMVP範囲外とすること

### FR-007: 簡易ログインと家庭単位データ

MVPでは簡易ログインを提供し、デモアカウントごとに1家庭のデータを扱う。

受け入れ条件:

- デモアカウントでログインできること
- 1アカウントに1家庭の設定を紐づけられること
- 本番品質の同意管理や詳細な世帯メンバー権限管理はMVP範囲外とすること

### FR-008: 安全制御

生成メッセージは、Bedrock Guardrails とアプリケーションルールで安全制御する。

受け入れ条件:

- 攻撃的、強制的、操作的なメッセージを抑制すること
- 高リスク判定時はユーザーに警告すること
- 送信代行の表現はデモ上の演出とし、実際の自動送信は慎重に扱うこと

## 5. 非機能要件

### NFR-001: デモ理解性

審査員が短時間で、ジョーク、テーマ適合性、AI依存への風刺を理解できること。

### NFR-002: AWS活用の説得力

AWSマネージドサービスを使う理由が明確であること。  
現時点で主な構成は未決定だが、Workflow Planningで以下を比較する。

- 基本サーバーレス構成
- Bedrock Flows中心構成
- AppSync Events中心構成
- AgentCore中心構成

### NFR-003: 事業性

Free / Standard / Pro の3プランでマネタイズ可能性を示す。  
価格が上がるほどユーザーが何も考えなくてよくなる構造を、テーマ性と収益性の両方として扱う。

### NFR-004: セキュリティ

セキュリティ拡張ルールは、PoC/プロトタイプ扱いのためブロッキング制約としては適用しない。  
ただし、家庭内メッセージや疑似バイタル情報はセンシティブな題材であるため、資料上は同意、取り消し可能性、安全制御の考慮を明記する。

### NFR-005: テスト方針

Property-Based Testingは一部適用する。  
対象は純粋関数とシリアライズ往復テストに限定する。

適用候補:

- 地雷ワード検出
- 炎上リスクスコア計算
- プラン別制御ロジック
- 家庭設定や会話履歴のJSON保存・復元
- 疑似バイタル情報の入力正規化

対象外:

- 生成AIの自然文品質そのもの
- UIの見た目
- 外部AWSサービス呼び出しの実統合

## 6. MVP範囲

### MVPに含める

- モバイルファーストWebアプリケーションとしての体験設計
- 不満入力から言い換え結果表示までの基本フロー
- 家庭内炎上リスクと地雷ワード検出
- Free / Standard / Pro のプラン差
- Proの疑似バイタル情報入力
- AI同士の家族会議シミュレーション
- 簡易ログインと1家庭デモデータ
- アーキテクチャ検討資料
- ピッチ・企画資料

### MVPに含めない

- 実スマートウォッチ連携
- 本番品質の同意管理
- 実際の自動メッセージ送信
- 本番運用レベルの認証・認可
- ネイティブモバイルアプリ
